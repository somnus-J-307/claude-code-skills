# 提示词工程：从"怎么问"到"怎么编排"的完整演化史

> 横纵分析法深度研究报告
> 日期：2026-05-27
> 研究对象：提示词工程（Prompt Engineering）

---

## 纵向分析：一部"与机器对话"的技术演化史

### 序章：前提示词时代（2018年以前）

2018年以前，NLP 处于"一个任务一个模型"的监督学习时代。情感分析要训练一个模型，机器翻译要训练另一个，摘要又是一个。没有"通用指令"的概念，模型是工具箱里的螺丝刀——每把只能拧一种螺丝。

那个时代的"提示词"本质上是数据预处理：分词、去停用词、构造特征向量。人类工程师把所有智慧都花在了"怎么让数据更适合模型"上，而不是"怎么让模型理解我的意图"。

转折点出现在 2018 年。Jeremy Howard 和 Sebastian Ruder 提出的 ULMFiT 证明了一件事：语言模型可以在大规模语料上预训练，然后迁移到各种小任务上。这个发现彻底改变了游戏规则——我们终于可以训练一个"懂语言"的通用模型，然后用自然语言告诉它要做什么。

同年，OpenAI 发布了 GPT-1，Salesforce 在 The Natural Language Decathlon 中首次提出"用自然语言描述任务本身"。现代提示词工程的概念起源，就在这里萌芽。

---

### 第一幕：GPT-3 的震撼与 In-Context Learning 的诞生（2020）

2020年5月，OpenAI 发布了 GPT-3。1750亿参数。这个数字本身就是一种宣言：暴力可以创造奇迹。

但真正改变世界的不是参数量，而是一个叫做 **In-Context Learning** 的能力。Brown 等人在那篇引用量超过 20,000 次的论文中定义了三种 prompting 范式：

- **Zero-shot**：直接给任务，不给示例
- **One-shot**：给一个示例
- **Few-shot**：给几个示例

这个发现的意义在于：**你不需要重新训练模型，只需要在输入里加几个例子，它就能学会新任务。**

提示词工程作为一个学科，正式诞生。研究者和开发者开始意识到：同样的模型，不同的提问方式，输出质量可以天差地别。"怎么问"第一次成为关键问题。

---

### 第二幕：技术爆发年——2022年的突破群

如果说 2020 年是奠基，那么 2022 年就是爆发。这一年，提示词工程的核心技术密集涌现，彻底改变了这个领域的面貌。

**2022年1月，Chain-of-Thought (CoT) 横空出世。**

Google Brain 的 Jason Wei 等人发现：如果在 prompt 中提供逐步推理的示例，模型在算术、常识和符号推理上的表现会显著提升。这项技术被引近 30,000 次，是提示词工程的定义性里程碑。

更令人惊讶的是，CoT 是一种"涌现能力"——只有在 1000亿+ 参数的大模型上才有效。这意味着，规模本身就是一种质变。

**2022年，Zero-Shot CoT 出现。**

Kojima 等人发现，只需在 prompt 后追加一句"Let's think step by step"，就能激发模型的推理能力，无需手工编写推理示例。这个发现证明了一件事：模型已经具备潜在的推理能力，只是需要一个简单的触发器。

**2022年，Self-Consistency 提出。**

Wang 等人用高温度采样多条推理路径，再通过多数投票选最终答案。这替代了朴素的贪心解码，进一步提升了 CoT 的鲁棒性。

**2022年，ReAct 框架诞生。**

Yao 等人将推理（Reasoning）与行动（Acting）交替进行：模型先思考，再调用工具执行操作，再根据结果继续推理。这为 AI Agent 和工具使用奠定了 prompting 基础。

**2022年11月，ChatGPT 发布。**

这是提示词工程进入大众视野的标志性事件。数亿用户开始实际体验 prompting，"Prompt Engineer"成为新兴职业。提示词工程从学术研究走向大众实践。

同一年，Anthropic 成立，提出 Constitutional AI 理念——模型应根据一套书面规则来评估自身 prompt 和回答的安全性。这为后来的结构化 prompting 奠定了安全框架。

---

### 第三幕：应用爆发与生态繁荣（2023）

2023年，GPT-4 发布，更强大的模型对复杂 prompt 响应更好，推动了提示词工程向更精细的方向发展。

**Tree of Thoughts (ToT)** 将线性 CoT 扩展为树状结构：模型可生成多条推理路径、评估潜力、决定分支方向并支持回溯。这适用于规划、创意写作和复杂问题解决。

**DSPy** 的出现标志着自动提示词优化的开端。这个由 Stanford NLP 提出的框架用编译器自动优化 prompt 和 in-context 示例，而非手动调试。它证明了一件重要的事：**系统化编排可以让小模型超越手动 prompting 的大模型。**

同一年，LangChain 等框架兴起，标准化了 prompt chaining 和 Tree-of-Thought 方法。提示词工程从手工操作走向工程化。

但2023年也有阴影。Prompt Injection 和 Jailbreaking 成为安全焦点，提示词安全从学术研究话题升级为实际的网络安全关切。Anthropic 发布了系统化的提示词工程教程，推动社区知识标准化。

---

### 第四幕：自动化与形式化（2024）

2024年，Claude 3 系列、GPT-4o 和 Gemini 系列相继发布，多模态模型模糊了 prompting 和编程的边界。

**Structured Output Prompting** 和 **JSON Mode** 成为标准，模型开始原生支持结构化输出。prompt 工程向数据格式化方向发展。

DSPy 生态成熟，自动 prompt 优化库涌现。提示词优化从手工调试走向可编程的系统化流程。

但更重要的是，**Prompt Engineering 开始被重新定义为"AI 编排"**。独立的 prompt 技巧让位于系统级的 AI workflow 设计。

---

### 第五幕：上下文工程时代（2025-2026）

2025年，**Context Engineering（上下文工程）** 概念被 Anthropic 等推广。这是一次范式转移：从写静态 prompt 转向动态管理模型的上下文窗口——包括记忆、检索（RAG）、外部数据库集成。上下文窗口被视为一个动态演化的环境。

**MCP 协议** 由 Anthropic 提出并被主要厂商采纳，标准化了 AI 工具和数据集的集成方式，成为 agent 架构的基础设施。

**Harness Engineering** 和 **Intent Engineering** 兴起。用规则、linter 和严格反馈环来约束 agent 的解空间；将高层目标转化为 agent 可执行的规则。

到2026年，**Agent Memory** 和自动 prompt 优化成熟。Anthropic 部署原生 Agent Memory，AI 生成的 prompt 证明常优于人工编写的指令。**Specification Engineering** 兴起——从对话式文本转向 agent 可消费的结构化文档。

**Prompt Engineer 职位开始消退**，合并为跨学科的 AI 工程和 workflow 自动化角色。

---

### 演化主线总结

```
监督学习专属模型 (pre-2018)
    → 预训练+微调范式 (2018: GPT-1, ULMFiT)
    → 零样本迁移 (2019: GPT-2)
    → In-Context Learning / Few-shot Prompting (2020: GPT-3)
    → 推理增强 prompting (2022: CoT, Zero-Shot CoT, Self-Consistency)
    → Agent 与工具使用 (2022: ReAct)
    → 自动 prompt 优化 (2023: DSPy)
    → 多模态 prompting (2023-2024: GPT-4V, Gemini)
    → 上下文工程 / Agent 编排 (2025-2026: Context Engineering, MCP)
```

## 横向分析：谁在做，做得怎么样

### 竞品判断：场景C——竞品充分

提示词工程领域已有成熟的商业工具、开源框架和平台生态。选取最具代表性的 5 个进行深入对比。

---

### 1. LangChain / LangSmith：生态最完整的"瑞士军刀"

**它活成了什么样：**

LangChain 是提示词工程领域的"React"——几乎所有 LLM 应用开发者都用过或至少听说过。它的核心价值不在于单点功能，而在于生态完整性：Prompt 管理、版本控制、链式调用（Chains）、Agent 编排、评估测试、追踪日志，全部集成在一个框架里。

用户选择它的理由通常是"它什么都能做"。但这个优点也是它的缺点——学习曲线陡峭，抽象层过多可能导致调试困难。很多开发者的体验是：入门时觉得"好方便"，深入后觉得"好复杂"。

**真实口碑：**
- 优点：生态最完整，集成 100+ LLM 提供商，社区活跃，文档丰富
- 槽点：抽象层太多，调试困难，部分功能需付费，"为了用 LangChain 而学 LangChain"

**生态位：** LLM 应用开发的"全家桶"，适合需要完整工具链的团队。

---

### 2. DSPy：学术血统的"编译器"

**它活成了什么样：**

DSPy 是 Stanford NLP 的作品，骨子里带着学术基因。它的核心理念是"编程而非提示"——用声明式的 Signature 定义任务，用 Module 封装可复用组件，用 Optimizer（Teleprompter）自动搜索最优 prompt。

DSPy 证明了一件重要的事：**系统化编排可以让小模型（如 Llama-2-13b）超越手动 prompting 的大模型（如 GPT-3.5）。** 这不是修辞，是有论文支撑的实验结果。

用户选择 DSPy 的理由通常是"我想让 prompt 优化可重复、可自动化"。但代价是学习曲线陡峭，调试复杂。

**真实口碑：**
- 优点：模型无关、自动优化、学术背景扎实，真正解决"prompt 调参靠玄学"的问题
- 槽点：学习曲线陡峭，调试复杂，"为了用 DSPy 而学 DSPy"

**生态位：** 提示词自动优化的"学术标准"，适合需要系统化、可重复优化的团队。

---

### 3. Anthropic Claude Prompting：结构化 prompting 的"最佳实践"

**它活成了什么样：**

Anthropic 不只是做了 Claude，更定义了"怎么给 Claude 写 prompt"的行业标准。XML 标签分隔指令和数据、`<thinking>` 块让模型先推理再回答、预填充响应引导格式——这些做法已经成为结构化 prompting 的通用范式。

用户选择 Claude prompting 实践的理由是"它真的管用"。Anthropic 的官方文档不只是告诉你"做什么"，还告诉你"为什么"，这在 AI 公司里是罕见的。

**真实口碑：**
- 优点：XML 标签结构化清晰，官方文档权威且实用，Claude 对结构化 prompt 响应好
- 槽点：部分技巧仅适用于 Claude，跨模型通用性有限

**生态位：** 结构化 prompting 的"教科书"，适合追求高质量 prompt 设计的开发者。

---

### 4. OpenAI Playground：快速原型的"沙盒"

**它活成了什么样：**

OpenAI Playground 是很多人的 prompting 起点。交互式测试、实时参数调整、多 Prompt 比较——它把 prompting 变成了一种"实验"而非"编程"。

用户选择它的理由通常是"我想快速试试"。免费、易用、直接集成 API。但它的局限也很明显：仅支持 OpenAI 模型，缺乏高级功能，不适合生产环境。

**真实口碑：**
- 优点：免费易用，快速原型，直接集成 OpenAI API
- 槽点：仅支持 OpenAI 模型，缺乏高级功能，"玩具级"

**生态位：** Prompting 的"游乐场"，适合学习和快速验证，不适合生产。

---

### 5. PromptPerfect：专注优化的"搜索引擎"

**它活成了什么样：**

PromptPerfect 的定位很清晰：我只做 prompt 优化。ML 算法自动优化、A/B 测试、实时反馈——它把 prompting 变成了一种数据驱动的优化过程。

用户选择它的理由是"我想让 prompt 自动变好"。但代价是功能聚焦于优化，缺乏部署和监控能力。

**真实口碑：**
- 优点：自动化优化能力强，实时反馈机制有效
- 槽点：功能单一，缺乏全生命周期管理，"只管优化不管部署"

**生态位：** Prompt 优化的"专业工具"，适合需要 A/B 测试和持续优化的场景。

---

### 生态位分析

提示词工程的生态版图可以分为三层：

```
┌─────────────────────────────────────┐
│  应用层：AI Agent、Workflow 自动化    │  ← 我们要做的"提示词转换器"在这里
├─────────────────────────────────────┤
│  工具层：LangChain、DSPy、PromptPerfect │
├─────────────────────────────────────┤
│  基础层：OpenAI、Anthropic、Google    │
└─────────────────────────────────────┘
```

我们的"提示词转换器"定位在应用层——它不是要做一个通用的 LLM 框架，而是要解决一个具体问题：**把用户的口语化指令转换成工程化提示词**。

这个定位的优势是：专注、轻量、解决真实痛点。劣势是：需要依赖底层模型的能力，且可能被大平台的功能迭代"吞噬"。

---

### 趋势判断

**机会：**
1. 从"写 prompt"到"管理上下文"的范式转移中，存在大量新工具需求
2. AI Agent 编排需要更友好的 prompting 界面
3. 非技术用户的 prompting 需求被严重低估

**风险：**
1. 大平台（OpenAI、Anthropic）可能将 prompting 最佳实践内置到产品中
2. 自动 prompt 优化（DSPy 等）可能让"手动写 prompt"变得过时
3. 提示词工程作为独立职业正在消退，可能影响工具的市场空间

## 横纵交汇：我们站在哪里，要往哪里去

### 历史给我们的启示

纵向分析揭示了一个清晰的演化规律：**提示词工程的每一次重大突破，都是在减少人类需要显式表达的信息量。**

- GPT-3 的 In-Context Learning 让你不需要写训练代码
- CoT 让你不需要手工编写推理步骤
- DSPy 让你不需要手动调参
- Context Engineering 让你不需要把所有信息塞进 prompt

**我们的"提示词转换器"顺应了这个趋势：让用户不需要学习 prompting 技巧，只需要表达意图。**

### 竞争格局给我们的启示

横向分析揭示了一个市场空白：**现有的 prompting 工具都在服务"已经会写 prompt 的人"，而没有人在服务"还不会写 prompt 的人"。**

- LangChain 服务开发者
- DSPy 服务工程师
- PromptPerfect 服务优化师
- OpenAI Playground 服务实验者

**没有人在服务"我只是想让 AI 帮我做件事，但我不知道怎么写才有效"的普通用户。**

这就是我们的生态位。

### 我们的定位

```
用户说："帮我写个邮件"
    ↓
我们的工具："你是谁？收件人是谁？正式还是随意？大概想说什么？"
    ↓
用户回答后，生成一个结构化 prompt
    ↓
用户把这个 prompt 粘贴到任何 AI 工具里
```

**核心价值：不改变用户的工作流，只提升用户与 AI 对话的质量。**

这比做一个独立应用更轻量，比做一个框架更聚焦，比做一个插件更通用。

### 下一步

1. **设计转换规则**：从论文和实践中提取"什么样的 prompt 更有效"的规则
2. **构建示例库**：收集"差 prompt → 好 prompt"的转换案例
3. **实现 Claude Code Skill**：先做一个最小可用版本
4. **验证效果**：用 A/B 测试证明转换后的 prompt 确实更有效
